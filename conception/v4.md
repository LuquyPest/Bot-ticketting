# Conception — v4 : un outil de tickets dont Discord est un canal

> Statut : **proposition**, à valider avant tout code. Ce document fixe le cap, les décisions et le découpage en pull requests. Il est mis à jour par une PR quand une décision change.

## 1. Le but

Aujourd'hui le projet est un **bot Discord avec un dashboard**. La v4 en fait un **outil de support à héberger soi-même**, où Discord n'est plus qu'un canal parmi d'autres :

- une équipe peut l'utiliser **sans Discord du tout** : comptes propres, tickets par e-mail, portail web ;
- une communauté Discord garde **tout ce qu'elle a aujourd'hui**, sans rien refaire ;
- les deux peuvent se combiner dans un même espace (Discord + e-mail + portail).

Ce n'est **ni une copie de GLPI ni de Jira** :

- pas d'inventaire du matériel, pas de gestion de projet (sprints, backlog) ;
- on garde ce qui fait la différence : Discord traité comme un vrai canal, une installation en vingt minutes, une interface moderne, rien qui parte chez un tiers.

## 2. Ce qui ne change pas

Ces engagements valent pour chaque PR de la v4 :

1. **Une instance en v3 passe en v4 sans rien faire.** Les migrations s'appliquent au démarrage ; aucune donnée n'est recopiée ni renommée en masse.
2. **Discord reste un citoyen de première classe** : MP, salons, fils, commandes, panels, `/setup` fonctionnent comme avant.
3. **L'API v1 et les webhooks ne cassent pas.** Ce qui change de forme passe par une nouvelle version d'API.
4. **Chaque PR est livrable seule** : elle laisse le projet utilisable, testé, documenté (FR et EN), avec sa ligne de patchnotes.

## 3. Décisions de conception

### 3.1 Les identifiants gardent leur format

C'est la décision qui rend la v4 faisable. Le code fait référence plus de 900 fois à l'identifiant d'un serveur Discord, et chaque table stocke des identifiants Discord (auteur d'une note, personne assignée, membre du staff…). Plutôt que de tout réécrire :

| Quoi | Aujourd'hui | v4 |
|---|---|---|
| Espace (ex-« serveur ») | ID du serveur Discord | **Inchangé** pour un espace venu de Discord. Un nouvel espace reçoit un identifiant **du même format** (18 chiffres, généré) : base `ticketbot_guild_<id>`, routes, cache, tout reste valable |
| Compte du staff | ID Discord | **Inchangé** pour un compte existant. Un nouveau compte local reçoit un identifiant `u_<aléatoire>` |
| Demandeur (`tickets.owner_id`) | ID Discord, ou `mail:<empreinte>` depuis la v3.2 | Inchangé ; un demandeur du portail web devient `web:<empreinte>`. Une fiche contact (§3.4) regroupe les identités d'une même personne |

Conséquence : **aucune migration de données lourde**. Seuls les endroits qui **parlent à Discord** (environ 45 appels au client Discord, plus les événements) apprennent à traduire « espace » → « serveur Discord relié ».

### 3.2 Espaces

- La table globale `guilds` devient la table des **espaces** (même table, nouvelles colonnes) :

  | Colonne | Rôle |
  |---|---|
  | `name` | Nom de l'espace, indépendant de Discord (repris du nom du serveur pour un espace migré) |
  | `discord_guild_id` | Serveur Discord relié, ou `NULL` (égal à l'ID de l'espace pour un espace migré) |
  | `created_by` | Compte qui a créé l'espace |

- **Discord devient une intégration de l'espace** (Paramètres → Intégrations → Discord) : relier un serveur, le délier ; sans serveur relié, tout ce qui touche à Discord est masqué (salons, rôles, panels, `/setup`).
- Inviter le bot sur un serveur qui n'est relié à aucun espace **crée un espace** comme aujourd'hui : l'arrivée d'une communauté Discord reste aussi simple.
- Le propriétaire de l'instance crée un espace sans Discord depuis **Instance → Espaces**.
- Vocabulaire : « serveur » → **« espace »** dans l'interface et la doc ; « serveur Discord » quand on parle de Discord.

### 3.3 Comptes et connexion

- Table globale `accounts` (`id`, `email`, `display_name`, `password_hash`, `created_at`, `disabled`) et `account_identities` (`account_id`, `provider` = `discord` | `oidc:<fournisseur>`, `subject`).
- **Connexion Discord : inchangée.** À la première connexion en v4, le compte est créé à la volée avec `id` = ID Discord : rien à migrer.
- **Connexion par e-mail et mot de passe** : hachage `scrypt` de Node (aucune dépendance), 2FA existante réutilisée, réinitialisation par lien envoyé par e-mail, limitation des tentatives (comme la connexion Discord), message identique que l'adresse existe ou non.
- **Invitations** : un fondateur invite par e-mail dans son espace, avec un rôle ; le lien (jeton à usage unique, haché en base, 7 jours) crée le compte ou l'ajoute à l'espace.
- **SSO d'entreprise (OIDC)** : Google, Microsoft, Keycloak, Authentik… configuré par le propriétaire de l'instance. Une identité OIDC se relie à un compte existant par l'adresse e-mail vérifiée seulement.
- Un même compte peut relier Discord **et** un mot de passe : Profil → Connexion.

### 3.4 Contacts (les demandeurs)

- Table par espace `contacts` (`id`, `display_name`, `email`, `notes`) et `contact_identities` (`contact_id`, `kind` = `discord` | `email` | `web`, `value`, la valeur étant ce qui est stocké dans `tickets.owner_id`).
- Une **fiche contact** remplace le profil membre actuel : tous les tickets d'une personne, quel que soit le canal, ses étiquettes, l'historique.
- **Fusion de contacts** : quand on sait que `@pseudo` sur Discord et `marie@exemple.fr` sont la même personne. Les tickets ne bougent pas ; la fiche regroupe les deux identités.
- Les réponses partent par le canal du ticket (MP, e-mail, portail) : c'est déjà le cas pour Discord et l'e-mail (`sendToMember`).

### 3.5 Démarrer sans Discord

- `DISCORD_TOKEN` devient **facultatif**. Sans lui : le dashboard, l'API, l'e-mail, le portail et les automatismes tournent ; les tâches propres à Discord (santé du serveur, synchronisation des rôles, commandes) sont sautées.
- **Propriétaire de l'instance sans Discord** : le premier compte est créé avec un jeton d'installation affiché par `scripts/setup.sh` (ou dans les logs au premier démarrage). Les propriétaires Discord actuels (propriétaire de l'application, `OWNER_IDS`) le restent.
- `setup.sh` demande si Discord est utilisé ; si non, il ne demande ni token ni Client Secret.
- **E-mail de l'instance** (Instance → E-mail) : un SMTP pour les invitations, les liens de connexion et les réinitialisations, distinct des boîtes de support de chaque espace.

### 3.6 Portail public

- L'espace membre (`/espace`) s'ouvre **sans compte Discord** : connexion par **lien envoyé par e-mail** (jeton à usage unique, 15 minutes), ou Discord comme aujourd'hui.
- Ouvrir un ticket depuis le web sans Discord ; suivre et répondre comme aujourd'hui.
- Plus tard (v4.1) : un **widget** à coller sur un site.

## 5. Sécurité

- Mots de passe : `scrypt` (sel par compte, paramètres stockés avec le hash), jamais journalisés ; 2FA imposable par espace comme aujourd'hui.
- Jetons (invitation, lien de connexion, réinitialisation, installation) : aléatoires, **hachés en base**, usage unique, durée courte, invalidés à l'usage.
- Pas d'énumération de comptes : même réponse et même temps de réponse que l'adresse existe ou non.
- OIDC : `state`, `nonce` et PKCE ; liaison uniquement sur e-mail **vérifié** par le fournisseur.
- Séparation inchangée : une base par espace, permissions vérifiées côté serveur, journal de chaque action.
- Chaque PR de la v4 se termine par une revue de sécurité de ses nouvelles surfaces, notée dans sa description.

## 6. Ce que ça change pour qui utilise déjà le bot

- **Rien d'obligatoire.** Après la mise à jour, la connexion Discord, les serveurs (devenus espaces) et toutes les fonctions restent là.
- En plus, au choix : un mot de passe sur son compte, des collègues invités par e-mail, un espace sans Discord, un portail ouvert aux personnes sans Discord.
- Un guide « Passer à la v4 » accompagne la PR 10.

## 7. Questions ouvertes

À trancher avant la PR concernée :

1. **Nom du projet** (PR 10) : « Ticket Bot » décrit mal un outil qui n'est plus un bot. Garder, ou choisir un nom ?
2. **Comptes partagés entre espaces** (PR 2) : un compte voit tous les espaces où il est membre (comme aujourd'hui avec Discord). À confirmer.
3. **Facturation, multi-instance** : hors sujet ; l'outil reste auto-hébergé, une instance par organisation.
