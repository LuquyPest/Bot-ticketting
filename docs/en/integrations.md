# Integrations

## Discord panels

**Panels** (founders): post a message with **buttons** in a channel to open a ticket without going through DMs. Customisable embed (title, description, colour, image), up to 25 buttons with label, emoji, style and subject, and an optional form opened on click. Editing the panel updates the message; deleting it removes the message.

## Public API

Turned on per space (**Settings → Integrations → Public API**), with **API keys** (**API keys** page) created by the founders: permissions of your choice, optional expiry date. Only a fingerprint of the key is stored. The same keys work for both versions.

**v2** (recommended for a new tool):

| Method | Route | Permission |
|---|---|---|
| `GET` | `/api/v2/space` (the key's space and permissions) | any key |
| `GET` | `/api/v2/tickets?status=open\|closed&contact_id=&limit=&cursor=` | `read_tickets` |
| `GET` | `/api/v2/tickets/:id` (ticket, messages, attachments) | `read_tickets` |
| `GET` | `/api/v2/tickets/:id/attachments/:fileId` (download) | `read_tickets` |
| `POST` | `/api/v2/tickets/:id/close` | `close_tickets` |
| `GET` | `/api/v2/contacts?q=&limit=&cursor=` | `read_contacts` |
| `GET` | `/api/v2/contacts/:id` | `read_contacts` |
| `GET` | `/api/v2/stats` | `read_stats` |

Lists answer `{ "data": [...], "next_cursor": "…" }`: pass `next_cursor` back as `?cursor=` for the next page, `null` at the end (100 items per page at most, 50 by default). A ticket gives its requester with their type (`owner.kind`: `discord`, `email` or `web`), its contact card (`contact_id`), its stage and its tags. Contacts expose their identities, never the staff's internal notes; the `read_contacts` permission is ticked separately.

**v1**, kept unchanged:

| Method | Route | Permission |
|---|---|---|
| `GET` | `/api/v1/tickets?status=open\|closed&page=1` | `read_tickets` |
| `GET` | `/api/v1/tickets/:id` (ticket and messages) | `read_tickets` |
| `POST` | `/api/v1/tickets/:id/close` | `close_tickets` |
| `GET` | `/api/v1/stats` | `read_stats` |

The key goes in the `Authorization: Bearer <key>` header. The **OpenAPI 3** description is public on `/api/v2/openapi.json` and `/api/v1/openapi.json`, and the **API documentation** page of the dashboard shows it with a `curl` example and a sample response for each route. Confidential tickets are never reachable through the API.

## Outgoing webhooks

**Settings → Integrations**: an HTTPS address notified when a ticket opens, closes or is taken (`ticket_open`, `ticket_close`, `ticket_claim`).

- `X-TicketBot-Event` header, and an `X-TicketBot-Signature-256` signature (HMAC-SHA256) if a secret is set.
- Private and internal addresses refused (SSRF protection), 5-second timeout.
- Confidential ticket: only `{ ticketId, confidential: true }`.

## Push notifications

Each staff member can get new messages and replies as browser notifications (**Profile → Notifications**), only for the tickets they can see. This needs the `VAPID_*` keys of `.env`, generated by `setup.sh`.

## Guest access

**Guest access** (founders): a temporary read-only link to chosen tickets, for an outside person without a Discord account (a partner's moderator, an adviser…). From one hour to 30 days, internal notes included or not, each view written to the log, revocable at any time.

## Tickets by e-mail

For people who are not on Discord: each e-mail received on the support address opens a ticket, exactly like a DM to the bot (same channel, or thread, or no channel; same subjects, rules and automations). **Settings → Integrations → Tickets by e-mail**, founders:

| | |
|---|---|
| **Address** | The support one (`support@your-domain`), with an optional display name |
| **Receiving (IMAP)** | Server, port 993 (TLS) or 143, username and password of the mailbox: it is read **every minute**, each handled e-mail is marked as read |
| **Sending (SMTP)** | Server, port 587, 465, 25 or 2525, username and password: replies go out from the support address |

**Test the connection** checks both before turning it on. Passwords are encrypted in the database (`ENCRYPTION_KEY`) and never shown again.

### Gmail and Microsoft 365, without a password

Google and Microsoft refuse ordinary passwords in IMAP and SMTP (Microsoft turned this sign-in off, Google requires app passwords). In **Mailbox connection**, pick **Google (Gmail, Workspace)** or **Microsoft 365 (Outlook)**, then **Sign in with…**: you pick the support mailbox at the provider and allow Datick to read it and send from it.

- Servers and account are set on their own; no password is stored. Datick keeps an **access token** renewed on its own, encrypted in the database like the passwords.
- **Reconnect** if the provider withdraws the access (account password changed, access revoked): the error message under the settings says so. **Disconnect** removes the access (at Google it is revoked too) and stops reading the mailbox.
- The owner of the instance must first declare the application, once for all spaces: [Instance → Connexion → Mailboxes](./instance#mailboxes-gmail-microsoft-365).

### Receiving by webhook (Mailgun, Postmark, SendGrid, Amazon SES)

Instead of reading the mailbox every minute, an e-mail service can **send each message to Datick as soon as it arrives**. In **How e-mails arrive**, pick **Sent by a service (webhook)** and the service, then paste the **reception address** shown there at the service (it holds a secret of the space):

| Service | Where to paste it | Check |
|---|---|---|
| **Mailgun** | *Receiving → Create route*, `forward` action to the address (add `/mime` at the end to get the raw message) | The **webhook signing key** (*Sending → Webhooks*): each request is signed, a replayed request is refused |
| **Postmark** | *Default Inbound Stream → Settings → Webhook URL*; tick *Include raw email content* for the original message | The secret of the address |
| **SendGrid** | *Settings → Inbound Parse*, with **POST the raw, full MIME message** ticked | The secret of the address |
| **Amazon SES** | A receipt rule with an **SNS** action (Base64 encoding) to a topic, then an HTTPS subscription of the topic to the address (confirmed on its own) | **Amazon's signature** on each message, and the given **topic ARN** |

An e-mail received this way follows exactly the path of one read from the mailbox: threads, rules, attachments, automatic replies ignored. **Replies** still leave through the mailbox's **SMTP** (or Google / Microsoft). **New address** replaces the reception address (if it leaked): the old one stops working at once. An error (signature refused, raw message missing) shows under the settings.

**What goes out by e-mail**: everything the bot would have sent by DM — acknowledgement, staff replies (dashboard, `/reply`, templates), stage changes, closing. The subject carries `[#<ticket>-<token>]`: an answer lands in its ticket only with this token **and** from the address that opened it — a forged sender cannot write into someone else's ticket. A **new e-mail**, without this token nor answering a message from the support, opens a **new ticket**, even if the person already has one open. When they have several open tickets, each staff reply goes in the thread of the ticket it is about.

**Ignored**: automatic replies (out of office, `Auto-Submitted`), bounces, mailing lists, the support address itself; beyond 10 e-mails per hour from the same sender. The quoted text of the previous message is removed. The person can also follow their tickets in the [member space](./member-space), signed in with a link received by e-mail.

**Several addresses**: under **Other addresses**, add addresses that arrive in **the same mailbox** (aliases or redirections: `billing@`, `tech@`…), up to 20. For each:

| | |
|---|---|
| **Subject** | The ticket's subject (among those of Settings → Tickets); the e-mail's subject line stays at the top of the first message. Without a subject: the e-mail's subject line, as for the main address |
| **Tag** | Added to the ticket when it opens: with the [roles linked to tags](./team#roles-tied-to-tags), the ticket goes to that team |
| **Reply from this address** | The ticket's replies leave from this address, with its display name. Your sending server must accept this address as sender; otherwise leave it unticked: replies leave from the main address, in the same thread |

The receiving address is recognised in `To`, `Cc`, or the headers added by the mailbox (`Delivered-To`, `X-Original-To`) for a redirection. Subject rules then apply as usual. An e-mail coming from one of these addresses is ignored (no loop). Every addition, change or removal is in the journal.

**Attachments**: kept on the server, downloadable from the ticket view (under their message, preview for images), with the same rights as the ticket. Everything is set in the same section:

| Setting | Default |
|---|---|
| Keep the attachments | yes (otherwise, only their name is noted) |
| Maximum size per file | 10 MB (up to 25) |
| Total space of the server | 500 MB; beyond it, new ones are no longer kept |
| Keep after the ticket is closed | 90 days (0 = forever); deleted every night after that |
| Refused types | executables and scripts (`exe`, `bat`, `js`, `html`, `svg`…), editable |
| Also post in the Discord channel | yes, up to 8 MB per file |

The space used is shown, with **Apply the retention now** and **Delete those of closed tickets**. A refused attachment is noted with the reason (« type refused », « over 10 MB »…). Files live in the `attachments` Docker volume, outside the nightly database backups.

::: tip Mail server on your local network
For safety, the IMAP and SMTP servers must have a public address (the bot never connects to an internal address chosen from the dashboard). For a mail server at home, `EMAIL_ALLOW_PRIVATE_HOSTS=true` in `.env`.
:::

## Web widget

A ticket form to paste on **your site**, for people without a Discord account. **Settings → Integrations → Web widget**:

1. Tick **Turn the widget on**. Optionally list the **sites allowed** to show it (one per line, `https://example.com`); empty, any site can show it.
2. **Save** gives the code to paste before the end of the `<body>` tag:

   ```html
   <script src="https://your-domain/widget.js" data-datick-widget="…" async></script>
   ```

   A **Support** button appears at the bottom right and opens the form. Options: `data-label` (button text), `data-color` (`#5865f2`), `data-lang` (`fr`, `en`, `es`, `de`, `it`, `pt`; otherwise the browser's language), `data-mode="inline"` (the form shows where the code is, height set with `data-height`).

The person gives their name (optional), their **e-mail address**, the subject if the space offers some, and their message. The ticket is theirs as in the [member space](./member-space) without Discord: the confirmation and the staff's answers reach them through the [e-mail of the instance](./instance#e-mail-of-the-instance), with the link to follow and answer in the member space. **Without the e-mail of the instance, the form stays unavailable.** Custom fields and the intake form are not asked by the widget. If the [public knowledge base](./member-space#public-knowledge-base) is online, the articles that look like the message are suggested while typing, each opened in a new tab.

**Anti-spam**, with no third party: a hidden field only robots fill in, at least 3 seconds between opening the form and sending it (signed time, valid 2 hours), **5 sends per hour per IP address**, **3 per e-mail address**, 60 new web tickets per hour for the space, the space's daily ticket limit and the blacklist. **New code** invalidates the code already pasted (in case of abuse); every change is in the journal.

## Backing up the configuration

**Settings → Backup**: JSON export of the configuration (settings, grades, tags, forms, panels, fields, FAQ and articles, templates and macros, rules, checklists, custom statuses, teams) and import on this server or another. Secrets are never exported.

The import merges by name and deletes nothing. A macro that changes the status finds the status with the same name in the target space. A status's Discord category is only carried over if you tick the channels option. Teams come with their settings, subjects and tags, but without members: those are accounts of each space, and a team already there keeps its own.

## Coming from another ticket bot

**Settings → Backup → Import from another bot** takes over the **still open** tickets of another bot (Ticket Tool, Tickets, Helper.gg…), without deleting anything:

1. pick the Discord category where the other bot keeps its tickets, then **Scan**;
2. for each channel, the dashboard finds the member who opened it (in the channel's permissions, or a mention in its topic); channels without an identifiable member are flagged;
3. tick the channels to take over and **Take over**: each one becomes a ticket of this bot.

Options: copy the last 100 messages of the channel into the ticket history (the member's messages and the staff's replies; those of bots are ignored), tell each member by DM — in their language — that they can now reply to the bot, and move the channels into the « Open » category. Then remove the old bot from your server: new tickets go through this one.

Old tickets **already closed** are not imported: none of these bots lets you export its data. Keep their transcripts where the other bot put them.
